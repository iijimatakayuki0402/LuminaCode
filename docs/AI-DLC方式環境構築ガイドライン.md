# AI-DLC方式 環境構築ガイドライン

## 0. 位置づけ

本ガイドラインは、Claude（Claude Code）のみを用いて AI-DLC 方式で開発環境構築を行うための共通手順・ルールを定義するものです。
プロジェクトごとに用意される **システム要件書** ・ **システム要望書** と、本ガイドラインを組み合わせて、Claude がフォルダ内に開発環境を構築し、人が開発を開始できる状態まで持っていくことを目的とします。

本ガイドラインは固定文書ではなく、開発を進める中で得られた気づきを **禁止事項・注意事項** として随時追記していく前提の「育てるドキュメント」です。

関連ドキュメント: [`001_AIDLC開発ガイドライン.md`](./001_AIDLC開発ガイドライン.md)（全体方針）

---

## 1. 目的

- Claude によるプロジェクト環境構築の手順・判断基準を統一し、担当者・プロジェクトによってやり方がばらつくことを防ぐ。
- 「何を Claude がやり、何を人がやるか」の責務分担を明確にする。
- 環境構築の各ステップを記録・再現可能にし、後から見直せる状態にする。

## 2. 適用範囲

- 本ガイドラインは、新規プロジェクトフォルダにおける **開発環境構築フェーズ** を対象とする。
- 実装・テスト・レビューなど構築後の開発フェーズの詳細ルールは対象外（別ガイドラインで定義）。
- 対象 OS / シェルは原則 Windows + PowerShell（環境によって異なる場合は都度明記する）。

## 3. 役割分担

| 作業内容 | 担当 |
|---|---|
| シェル（CLI）で実行可能なツール・ランタイム・パッケージのインストール、バージョン切替、環境変数設定 | **Claude** |
| インストーラの GUI 操作、ライセンス同意ダイアログ、対話式ウィザードが必須なインストール | **人** |
| システム要件書・システム要望書の作成・承認 | **人**（Claude は下書き支援のみ） |
| 技術スタック・ツール選定の提案 | Claude が提案し、**人が承認** |
| 破壊的操作（既存フォルダ削除、既存設定の上書き、外部リソースへの接続確立など）の実行判断 | Claude が事前提示し、**人が承認**してから実行 |
| 環境構築後の動作確認 | Claude が実行し、結果を人に報告 |

原則: **CLI で完結する作業は Claude が行い、GUI 操作が必須な作業のみ人に依頼する。** Claude は GUI 操作が必要になった時点で作業を止め、人に「何を」「なぜ」「どの手順で」実施してほしいかを明示する。

## 4. インプットドキュメント

環境構築を始める前に、以下がプロジェクトフォルダ内に存在することを確認する。無ければ Claude は着手前に人へ確認する。

1. **システム要件書**（機能要件・非機能要件・使用技術の制約など）
2. **システム要望書**（要件書ほど厳密でない、実現したいことや優先度・希望）

これらが揃っていない、または内容が矛盾・不足している場合、Claude は推測で進めず、不足点を人に確認する。

## 5. 環境構築フロー

各ステップの完了時に、簡潔な報告（何をしたか／次に何をするか）を行う。

### Step 0. ガイドライン・入力確認
- 本ガイドライン、および現在の禁止事項・注意事項（第9章・第10章）を確認する。
- システム要件書・システム要望書を読み込む。

### Step 1. 要件整理
- 要件・要望から「必要な技術スタック（言語・フレームワーク・DB・インフラ等）」「開発に必要なツール一覧」を洗い出す。
- 不明点・矛盾点があれば人に確認する。

### Step 2. 構築計画の提示
- 導入するツール・バージョン・フォルダ構成の方針を人に提示し、承認を得る（Plan Mode 等を用いて合意形成する）。
- 既存フォルダ・既存ファイルに影響する場合は、影響範囲を明記する。

### Step 3. ツール・ランタイムのインストール（Claude 実施）
- シェルで実行できるインストール作業（言語ランタイム、パッケージマネージャ、CLI ツール、エディタ拡張の CLI 設定等）を Claude が実行する。
- GUI 操作が必須なインストーラに当たった場合は作業を中断し、以下を人に伝える。
  - インストール対象・目的
  - ダウンロード元・実行するインストーラ名
  - 必要な操作手順
  - 完了後に Claude 側で確認すべきこと（PATH 追加確認等）

### Step 4. プロジェクト初期化
- フォルダ構成の作成（第6章の標準構成を基準に、要件に応じて調整）。
- 設定ファイル（`.gitignore`、パッケージ管理ファイル、Lint/Format 設定、環境変数テンプレート等）の作成。
- 必要に応じて Git 初期化（実施の是非・リモート接続は人に確認してから行う）。

### Step 5. 動作確認
- Hello World 相当の起動確認、ビルド確認、Lint/フォーマッタ実行、テストランナーの起動確認など、「開発を始められる状態」であることを検証する。
- 確認項目と結果を人に報告する。

### Step 6. 開発開始判定
- Step 0〜5 の完了と、未解決の懸念事項（あれば）を人に報告し、開発フェーズへの移行可否を確認する。

## 6. 標準フォルダ構成（基準）

プロジェクトの技術スタックに応じて調整するが、特筆すべき事情がない限り以下を基準とする。

```
プロジェクトルート/
├─ docs/                 要件書・要望書・設計書など
├─ src/                  ソースコード
├─ tests/                テストコード
├─ scripts/               環境構築・運用スクリプト
├─ .env.example           環境変数テンプレート（実値はコミットしない）
├─ .gitignore
└─ README.md              セットアップ手順・起動方法
```

## 7. ドキュメント管理ルール

- ガイドライン・要件書等は `連番3桁_ドキュメント名.md` の命名を基準とする（例: `001_AIDLC開発ガイドライン.md`）。ただし本ファイルのように主要ガイドラインは番号なしでも可とする。
- 内容を変更した場合は、本ファイル末尾の「変更履歴」に日付・変更内容を追記する。

## 8. 環境構築時の確認事項（安全対策）

- インストール・初期化コマンドを実行する前に、対象フォルダに既存の作業（未コミットの変更、既存ファイル）がないか確認する。
- 既存ファイルの削除・上書きが必要な場合は、事前に人へ確認する。
- 外部ネットワークへの接続、認証情報の入力・保存が必要な作業は、実施前に人へ確認する。

## 10. 注意事項

> 開発を進める中で判明した「気をつけるべきこと」をここに追記する。追記時は日付・理由をセットで記載する。

- **2026-09-28**: npmパッケージの `latest` dist-tag は必ずしも安定版ではない。ProjectHub構築時、`prisma` の `latest` が `8.0.0-rc.x` を指しており、無関係なCloudflare Workers関連パッケージ（workerd/alchemy）まで依存関係に引き込まれた。バージョン指定なしで主要パッケージを導入する際は `npm view <pkg> dist-tags` で `latest` の素性を確認し、必要なら安定版（`prev`タグ等）に明示的に固定する。
- **2026-09-28**: npm 11の install-scripts承認機能により、初回 `npm install` 時にネイティブビルド・postinstallスクリプトが自動実行されず警告が出ることがある（`npm warn allow-scripts`）。`npm approve-scripts <pkg>` で対象パッケージを個別確認のうえ承認する（`--all`による一括承認は避け、身に覚えのある依存かを都度確認する）。
- **2026-09-28**: Prisma 7 以降は `datasource.url` をスキーマに直接書けず、`prisma.config.ts` と driver adapter（例: `@prisma/adapter-better-sqlite3`）方式に変更されている。また `prisma.config.ts` 自体は `.env` を自動読込しないため、`process.loadEnvFile()` 等で明示的に読み込む必要がある。
- **2026-09-28**: Tailwind CSS v4 はPostCSSプラグインが `@tailwindcss/postcss` に分離され、`tailwind.config.ts` によるJS設定ではなくCSS内 `@theme` ブロックでのトークン定義が標準になっている。
- **2026-09-28**: ESLint 9 は `.eslintrc.*` を読まず、flat config（`eslint.config.mjs`等）必須。`eslint-config-next` の最新版はflat config配列をそのままexportしているため、`FlatCompat` は不要。
- **2026-09-28**: TypeScript 6.0 では `baseUrl` 単独指定や `moduleResolution: "node"`（node10）が非推奨警告になる。`paths` は `baseUrl` なしでも動作するため削除し、Node向けCommonJS出力には `module`/`moduleResolution` を `node16` に揃える。

- **2026-10-02**: Lumina Code構築時、peer依存の上限で最新版を採用できなかった。`electron-vite@5` は `vite` ^7 まで、`@vitejs/plugin-react@6` は `vite` ^8 必須、`typescript-eslint` は `typescript` <6.1 が条件。vite 7 / plugin-react 5 / TypeScript 6.0 / ESLint 9（`@eslint/js` も 9 に揃える）で固定した。`npm view <pkg> peerDependencies` で確認してから導入する。
- **2026-10-02**: `npm approve-scripts` は承認のみで、スクリプトは実行されない。承認後に `npm rebuild <pkg>` が必要。`electron` は `npm rebuild` でもバイナリが取得されず、`node node_modules/electron/install.js` を直接実行する必要があった。`better-sqlite3` は `electron-rebuild -f -w better-sqlite3` で Electron 用に再ビルドする（Node から直接読み込むと ABI 不一致になる）。
- **2026-10-02（上記の訂正）**: `better-sqlite3` v13 は N-API 版で、同梱の `prebuilds/` のバイナリを最優先で読み込むため、Node（ABI 137）と Electron 44（ABI 149）の両方で再ビルドなしに動作することを確認した。`electron-rebuild` による再ビルドは不要のため、`rebuild` スクリプトと `@electron/rebuild` の直接依存は削除した（`electron-builder` の間接依存としては残る）。Electron ランタイムでの確認は `npm run test:electron` で行う。
