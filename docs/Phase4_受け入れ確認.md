## 実装の要点

- **フォールバック（CHT-16）**：`fallbacks: "default"` はベータ `server-side-fallback-2026-07-01` と組み合わせる（配列の形は `-2026-06-01` で、組み合わせを間違えると 400 になる）。対応しないモデルは Models API からは分からないため、400（メッセージに `fallback` を含む）が返ったら付けずに送り直し、設定 `fallback.unsupported.<モデル>` に記録する（拡張思考のオフと同じ方式）。
- **送り返す内容（CHT-16）**：切り替わった回答は、最後の `fallback` ブロックより前の思考・ツール呼び出し・結果の無いサーバーツール呼び出しを除き、`fallback` ブロック自体も送らない（`src/main/chat/fallback.ts`）。
- **フォールバックの使用量**：上位の `usage` は回答したモデルの分だけのため、`usage.iterations` からモデルごとに分けて `usage_records` に記録する（1 つの回答に複数の行ができる）。拒否された試行も、報告された分はそのまま計上する（課金されない場合もあるため、概算は多めになることがある）。
- **生成途中の上限（USG-04）**：出力は `max_tokens` で上限を保証する。入力は、直前のリクエストの実測トークン数と新しいメッセージの文字数（1 文字 1 トークン、画像 5,000 トークン、PDF は大きさから）で多めに見積もる。生成中は、開始時の実際の入力、Web 検索の回数、受け取った文字数（4 文字 1 トークンで少なめに）で確かめる。トークン数を数える API は、追加の通信になるため使っていない。

## 確認して分かったこと・未確認の点

- 現在のモデルはすべて `fallbacks: "default"` を受け付けたため、「受け付けないモデルで送り直す」処理は、今のところ使われない（将来のモデルへの備えとして残す）。
- **実際に拒否されたときの動きは未確認**。安全上の分類器に意図的に拒否させる依頼は行わない方針のため。`fallback` ブロック・`usage.iterations` の扱いは、SDK の型と API の説明に沿ったテストで確認している。
- **フォールバック先のモデルの単価**：`max_tokens` は依頼したモデルの単価で決めるため、より高いモデルに切り替わった場合は、上限をわずかに超えることがある。
- 生成中の表示（「○○ で回答しています…」）は、実際に拒否されたときにしか出ないため、画面では確認していない（生成後の表示は画面で確認済み）。
